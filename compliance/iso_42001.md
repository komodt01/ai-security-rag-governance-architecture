# ISO/IEC 42001 AI Management System Mapping

## Purpose

This document maps the AI Security Governance and RAG Risk Architecture project to selected concepts from ISO/IEC 42001:2023.

ISO/IEC 42001 provides requirements for establishing, implementing, maintaining, and continually improving an Artificial Intelligence Management System (AIMS).

This project uses the standard as a governance and architecture lens.

> This repository is not an ISO/IEC 42001-certified AIMS, certification assessment, or formal conformance claim.

The purpose of this mapping is to show how the architecture considers:

- AI governance
- Ownership and accountability
- Use-case review
- Risk management
- Data governance
- Human oversight
- Lifecycle management
- Monitoring
- Incident response
- Supplier/provider governance
- Continual improvement

# Project Context

The production concept is an internal AI assistant that could eventually use Retrieval-Augmented Generation to help employees locate and understand approved enterprise information.

The project has progressed through:

```text
Architecture and Governance
        ↓
Local Security-Control Prototype
        ↓
Selected Control Validation
```

The local prototype uses:

- Synthetic users
- Synthetic roles and groups
- Synthetic documents
- Document metadata
- Simple keyword retrieval
- Pattern-based prompt-risk evaluation
- Role/group authorization
- Local JSONL logging
- Advisory response generation
- Simulated human-review triggers

It does not use:

- Production LLM
- Embeddings
- Vector database
- Enterprise identity provider
- Production SIEM
- Cloud AI
- External model provider
- Production human-review workflow
- Real enterprise data
- Autonomous agents

# Core Management Principle

The model should not become the authority for:

- Identity
- Access
- Data entitlement

- IAM Owner

# Accountability Principles

## AI Is Advisory

The current prototype cannot:

- Approve access
- Approve security exceptions
- Make production changes
- Make legal decisions
- Make compliance decisions
- Perform transactions

## Human Authority Remains External

Human accountability should be based on the consequence of the decision or action.

Examples may include:

- Access approval
- Security exception
- Production change
- Legal interpretation
- Regulatory decision
- High-impact business decision

## Administration Is Separate from Data Entitlement

An AI system administrator should not automatically receive access to all documents available to the AI system.

# AI Risk Assessment

The repository includes a dedicated AI risk assessment.

Risk is evaluated qualitatively based on factors such as:

- Business consequence
- Data sensitivity
- User population
- System authority
- Exposure
- Threat likelihood
- Control effectiveness
- Residual risk

The project intentionally avoids an additive 1–4 scoring model that could create false precision.

# Risk Treatment

Possible treatment options include:

- Mitigate
- Avoid
- Accept
- Transfer
- Defer
- Redesign
- Escalate

Formal acceptance belongs to the authorized organizational risk owner.

# AI Use-Case Intake

AI governance should begin with the business problem.

Important questions include:

- What problem are we solving?
- Why is AI needed?
- Who will use the system?
- What data will be processed?
- What decisions could AI influence?
- What could go wrong?
- What controls are required?
- Who owns the outcome?
- What evidence will be required?
- What happens if the AI is wrong?

This business-first approach helps prevent technology-first adoption.

# Possible Decision Outcomes

An organizational review process could result in:

- Approved
- Approved with conditions
- Limited pilot
- Escalated review
- Rejected
- Deferred

This repository documents the review concept but does not implement an enterprise approval system.

# Classification

The production concept may use classifications such as:

- Public
- Internal
- Confidential
- Restricted
- Regulated
- Secrets

The prototype uses synthetic Internal, Confidential, and Restricted labels.

No real sensitive enterprise data is used.

# Authorization

Classification does not equal authorization.

The system should still evaluate:

```text
Who is the user?
        +
What are they allowed to access?
        +
What is the document's policy?
```

The local prototype uses role OR group authorization against document metadata.

# Human Oversight

Human oversight should be proportional to consequence.

It should not be triggered automatically simply because:

- A document is Restricted
- A prompt receives a High label
- AI is involved

Examples requiring accountable human authority may include:

- Access approval
- Security exceptions
- Production changes
- Legal decisions
- Regulatory decisions
- Financial or customer-impacting decisions

# Local Human-Review Behavior

The prototype can generate a simulated review event when an authorized retrieved document contains:

```text
human_review_required
```

The current implementation:

- Logs the event
- Marks it as pending simulated review

It does not:

- Stop the response
- Assign a reviewer
- Record approval
- Record rejection
- Enforce an SLA

Therefore:

> The prototype demonstrates a human-review trigger, not a human-review approval workflow.

# Security Architect Perspective

ISO/IEC 42001 is useful because it forces AI security to be considered beyond the technical control plane.

The architecture needs to connect:

```text
Leadership Intent
       ↓
Governance
       ↓
Business Use Case
       ↓
Risk
       ↓
Architecture
       ↓
Controls
       ↓
Evidence
       ↓
Human Accountability
       ↓
Continual Improvement
```

That is a different question from simply asking which model or cloud service should be used.

The security architect's role is to help make those requirements enforceable in the architecture.
