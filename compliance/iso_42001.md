# ISO/IEC 42001 AI Management System Mapping

## Purpose

This document maps the AI Security Governance and RAG Risk Architecture project to ISO/IEC 42001:2023, the international standard for an Artificial Intelligence Management System.

The purpose is to show how the project supports responsible AI governance, risk management, lifecycle oversight, accountability, human review, data governance, monitoring, and continual improvement.

This mapping is intended as a practical security architecture alignment, not a formal certification assessment.

## Standard Context

ISO/IEC 42001:2023 specifies requirements for establishing, implementing, maintaining, and continually improving an Artificial Intelligence Management System, also known as an AIMS. It is designed for organizations that provide or use AI-based products or services and provides a structured way to manage AI risks and opportunities. :contentReference[oaicite:0]{index=0}

For this project, ISO/IEC 42001 is especially relevant because the architecture focuses on a governed internal AI assistant that uses Retrieval-Augmented Generation to answer employee questions from approved internal documents.

## Project Context

The project is designed for a regulated organization that wants to adopt an internal AI assistant while managing risks related to:

- Prompt injection
- Sensitive data disclosure
- Unauthorized document retrieval
- Weak auditability
- Overreliance on AI output
- Inadequate human review
- Model and vendor risk
- Data classification gaps
- AI incident response
- Cloud cost exposure
- Incomplete governance ownership

The project is intentionally documentation-first and local-first.

The local prototype uses:

- Mock users
- Mock roles
- Mock documents
- Mock document metadata
- Local logs
- Basic prompt injection detection
- Basic sensitive data detection
- Role-based retrieval filtering
- Human review simulation

No paid cloud services or real sensitive data are required.

## Risk Domains

| Risk Domain | Description |
|---|---|
| Data Risk | Sensitivity of documents, prompts, outputs, and logs |

## Risk Scoring

| Score | Rating | Description |
|---|---|---|
| 1 | Low | Limited risk; standard controls are sufficient |
| 2 | Medium | Moderate risk; documented controls required |
| 3 | High | Significant risk; security and governance review required |
| 4 | Critical | Major risk; legal, privacy, compliance, executive, or incident review may be required |

## Risk Treatment Options

| Treatment | Description |
|---|---|
| Accept | Risk is understood and accepted by accountable owner |
| Mitigate | Controls are implemented to reduce likelihood or impact |
| Transfer | Risk is handled through contract, vendor, insurance, or third party |
| Avoid | Use case is rejected or redesigned |
| Defer | More information is required before decision |

## AI Use Case Intake and Impact Review

ISO/IEC 42001-style governance requires understanding the intended use and potential impact of AI systems.

## Intake Questions

The project intake process asks:

- What business problem does the AI use case solve?
- Why is AI needed?
- What data will be used?
- Who will use the system?
- What decisions could AI influence?
- What risks are introduced?
- What controls are required?
- Who owns the use case?
- Who approves the use case?
- What monitoring is required?
- What happens if AI output is wrong?

## Decision Outcomes

| Decision | Description |
|---|---|
| Approved | Use case may proceed with documented controls |
| Approved with Conditions | Use case may proceed only after required controls are implemented |

| Escalated | Requires security, privacy, legal, compliance, risk, or architecture review |
| Rejected | Use case should not proceed |

## Data Governance and Data Classification

AI systems depend heavily on data quality, data classification, and data access rules.

## Project Data Governance Controls

| Control | Description |
|---|---|
| Classification Required | Documents must be classified before ingestion |
| Owner Required | Documents must have an accountable owner |
| Metadata Required | Documents must have status, roles, groups, review date, source, and version |
| Deny by Default | Missing metadata denies ingestion or retrieval |
| Restricted Data Handling | Restricted content requires approved roles and possible human review |
| Regulated Data Handling | Regulated data is prohibited in the local prototype |
| Secret Handling | Secrets are prohibited in prompts, documents, responses, and logs |
| Log Minimization | Full prompt and response logging should be avoided by default |
| Embedding Classification | Embeddings inherit classification from source content |

## Classification Levels

| Classification | Handling |
|---|---|
| Public | May be used if source is approved and current |
| Internal | Available to authenticated users where appropriate |
| Confidential | Requires approved roles or groups |
| Restricted | Requires explicit authorization and often human review |
| Regulated | Prohibited in local prototype; formal review required |
| Secrets | Prohibited; block and trigger incident response |

## AI Incident Response

The project includes AI-specific incident response procedures.

## Incident Categories

| Incident Type | Description |
|---|---|
| Prompt Injection Abuse | User attempts to bypass system instructions |
| System Prompt Leakage | Hidden instructions or control logic are exposed |
| Sensitive Data Exposure | Sensitive data appears in prompt, response, or logs |
| Unauthorized Retrieval | User accesses or attempts to access unauthorized documents |
| Poisoned Knowledge Base | Malicious or inaccurate content is ingested |
| Unsafe Output | AI generates risky or unsupported guidance |
| Human Review Bypass | High-risk output is released without required review |
| Excessive Usage | Prompt volume or cost spikes abnormally |
| Logging Failure | Required logs are missing or disabled |
| Administrative Misconfiguration | Access, model, prompt, or retrieval rules are changed improperly |

## Incident Lifecycle

| Step | Description |
|---|---|
| Detection | Identify suspicious or unsafe AI behavior |
| Triage | Determine severity, user, data, documents, response, and impact |
| Containment | Stop ongoing exposure or misuse |
| Investigation | Reconstruct prompt, retrieval, response, review, and log events |
| Eradication | Remove root cause |
| Recovery | Restore safe operation |
| Post-Incident Review | Capture lessons learned and improve controls |

## Security Architect Notes

ISO/IEC 42001 helps frame this project as more than a technical AI prototype.

It shows that secure AI adoption requires a management system approach:

- Define the AI use case
- Establish scope and ownership
- Assess risk
- Classify data
- Define access controls
- Monitor behavior
- Preserve evidence
- Require human oversight
- Respond to incidents
- Review suppliers
- Improve controls over time

This is especially valuable for security architecture because the role is not only to select tools, but to create safe, governed patterns that align AI adoption with business, risk, and compliance expectations.

## Conclusion

This project aligns well with ISO/IEC 42001 because it treats the AI assistant as a governed enterprise system rather than an unmanaged chatbot.

The project demonstrates practical AI management system concepts through architecture documentation, governance templates, risk assessment, data classification, access control, logging, human review, incident response, cloud deployment decision gates, and a cost-safe local prototype.

The recommended implementation remains local-first until the organization has approved data handling, provider review, logging, human oversight, incident response, and cost controls.
